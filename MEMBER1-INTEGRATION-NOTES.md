# Member 1 Module — User Management (patch)

These files drop straight into your existing `backend/` project at the
exact same paths — no restructuring needed.

## Files in this patch

| File | What it is |
|---|---|
| `util/PasswordUtil.java` | New. Hashes/verifies passwords (PBKDF2, no new dependency). |
| `dao/UserDAO.java` | New. Full read/write DAO for `users` (insert, findByEmail, findById, updateProfile, updatePassword). Leaves `AdminUserDAO` untouched — that class's `findAll()`/`findByRole()` still work fine for the Admin module. |
| `service/UserService.java` | New. Validation + business rules for register/login/profile/change-password. Same style as `NeedService` — throws plain `IllegalArgumentException` for bad input. |
| `controller/AuthController.java` | New. `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`. |
| `controller/ProfileController.java` | New. `GET /api/profile`, `PUT /api/profile`, `POST /api/profile/password`. |

No changes to `pom.xml`, `DBConnection.java`, `User.java`, or `UserRole.java` —
they already work and are reused as-is.

## How to apply

1. Copy each file into your real project at the matching path under
   `backend/src/main/java/com/careconnect/...` (or `webapp/` for `index_old.html`).
2. `mvn clean package` (or `mvn tomcat7:run` for local testing, since your
   `pom.xml` already has the plugin configured).
3. Test: `POST http://localhost:8080/api/auth/register` with body
   `{"fullName":"Test User","email":"test@example.com","password":"test123","phone":"9999999999","role":"DONOR","address":"Pune"}`
   — should return `201` with the created user (no password in the response).
4. Then `POST /api/auth/login` with `{"email":"test@example.com","password":"test123"}`
   — should return `200` with the user and set a session cookie.
5. Using that same session (e.g. Postman's cookie jar, or a browser),
   `GET /api/profile` should return the same user.

## For Member 2 / Member 3

Once this is merged, any controller can check who's calling like this:

```java
HttpSession session = req.getSession(false);
if (session == null || session.getAttribute("userId") == null) {
    // not logged in -> 401
}
Integer userId = (Integer) session.getAttribute("userId");
UserRole role = (UserRole) session.getAttribute("role");
```

That's the exact pattern used in `ProfileController.requireLogin()` — copy
it into `NeedController`, `InstitutionController`, `AdminController`, etc.
wherever you want to restrict who can call an endpoint (e.g. only an
INSTITUTION-role user who owns a given `institution_id` should be able to
edit its needs; only ADMIN should be able to hit `/api/admin/*`). None of
your existing controllers currently check this, so that's the natural next
step once this lands, but it wasn't touched here since retrofitting other
people's controllers isn't Module 1's call to make unilaterally.

## Note on `ADMIN` accounts

`/api/auth/register` deliberately rejects `role: ADMIN` (privilege
escalation risk). To create your first admin for testing/demo, insert a
row directly into MySQL with a password hash generated by
`PasswordUtil.hashPassword("your-password")` — e.g. run a throwaway
`main()` that prints the hash, then paste it into an `INSERT` statement.
